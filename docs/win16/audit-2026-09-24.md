# Nitemare3D pre Windows 3.x / 3.11 — audit všetkých dostupných verzií

Dátum: 24. 9. 2026. Platforma: Win16. Rozsah: priamo dodané EXE 1.3, 1.6, 1.8 a 1.10, ich Ghidra C exporty a dáta priložené k shareware 1.3/1.6/1.8.

## Výsledok a hranice

Audit overil identitu štyroch odlišných Windows buildov, vytvoril register **3 856 verziovaných funkčných blokov** a priniesol nové priame zistenia o časovaní, poradí aktualizácií, kalibrácii, palete, zvuku a rozdieloch máp. Rozbor opravil viacero starších tvrdení o časovaní. Dvanásť samostatne nahraných súborov `nite3w*.exe` sú totožné kópie referencie 1.10.

**Nie je to dokončenie všetkého neznámeho ani 3 856 ručných sémantických auditov.** Register je automatický štrukturálny inventár. Podrobná nová kontrola sa týka konkrétnych otázok uvedených nižšie. Získaných runtime záznamov v tomto audite: **0**. Ďalšie historické vydania alebo registrované varianty bez dodaných binárnych súborov nemožno označiť za preskúmané. Existenciu iných čísel verzií tento dokument nepredpokladá.

`Confirmed / High` znamená priamy statický dôkaz v bajtoch alebo dátach, nie automaticky experiment počas behu. `Inferred` označuje odvodený význam alebo dôsledok. `Unknown` zostáva otvorené. Adresy `3:xxxx` sú **poradové číslo NE segmentu a offset**, nie runtime selector, fyzická adresa ani Ghidra lineárna adresa. Ghidra `FUN_1010_xxxx` v týchto exportoch zodpovedá NE segmentu 3.

### 2.1 Nominálne 8 Hz a vynechané kroky

Win16 1.10 `3:D70E–D73B` vykonáva:

```text
bucket = ((uint32(time_ms) << 3) modulo 2^32) / 1000
if bucket != previous_bucket:
    previous_bucket = bucket
    logical_slow_counter += 1
return logical_slow_counter
```

Používa DS `022C` pre posledný bucket a DS `0228` pre logické počítadlo, oboje 32-bit. Pri dostatočne častom volaní je bežný rytmus 8 krokov/s, teda nominálne 125 ms medzi krokmi. **Vynechané buckety sa nedobiehajú:** po preskoku z 0 na 1 000 ms sa counter zvýši raz, nie o osem. Plánovač tiež neobsahuje slučku, ktorá by znovu vykonala všetky zmeškané slow update-y. Confirmed / High.

V režime `mode == 0` plánovač podľa tohto počítadla volá pomalú aktualizáciu. Pri `mode != 0` je osobitná vetva: aktualizácia je naviazaná na nepárnu render generáciu pred jej zvýšením, teda v súvislej tejto ceste na každý druhý frame. Globálna premenná je v 1.10 DS `46B8`; existujúce DEMO cesty ju používajú. Nie každú nenulovú hodnotu tu pomenúvame ako jeden univerzálny režim prehrávania.

**Dôsledok:** 125 ms nie je zaručený čas každého GUARD kroku za všetkých okolností. Pomalý stroj, pauzy, zmeny režimu a odlišné cesty môžu zmeniť skutočný čas. To však neoprávňuje nahradiť 8 Hz výrazom `1000 / DAT_53F2`.

### 2.2 Kalibrácia meria kreslenie, nie päť krokov AI

`3:D7D0` v 1.10 vykoná jeden prípravný render, zmeria **päť volaní `D7C0`**, pričom `D7C0` volá render `D78C`, nadväzujúcu HUD vetvu `BA54` a prezentáciu `3AB8`. V tejto meranej slučke nevolá `D974`.

Pri bežných kladných časových hodnotách je odvodený model:

```text
raw_mean_ms = floor(uint32(end_ms - start_ms) / 5)
DS:53F2 = low16(raw_mean_ms)       // zápis PRED spodným obmedzením
D = max(raw_mean_ms, 40)          // lokálna efektívna hodnota
DS:53F4 = floor((1000 + floor(D/2)) / D)
DS:53F6 = max(1, floor((D+2)/4))
DS:53F8 = max(1, floor((360*D+1400)/2800))
DS:53FA = 2 * DS:53F6
```

Príklad pri surovom priemere 10 ms: **53F2 ostane 10**, lokálne D je 40, frame rate 53F4 je 25, pohybový krok 10, uhlový krok 5, projektilový počet podkrokov 20. Zápis `53F2` na `3:D863` sa po lokálnom clampovaní na `D873` neopakuje. Potvrdené pre všetky štyri buildy. Extrémne signed/overflow prípady týchto výpočtov zostávajú samostatnou otázkou; pseudokód ich nezovšeobecňuje.

| Pole | 1.3 DS | 1.6 DS | 1.8 DS | 1.10 DS |
|---|---|---|---|---|
| Render generácia | `531A` | `53CC` | `53DC` | `53DC` |
| Surový priemer merania | `5330` | `53E2` | `53F2` | `53F2` |
| Kalibrované frame tempo | `5332` | `53E4` | `53F4` | `53F4` |
| Pohybový krok | `5334` | `53E6` | `53F6` | `53F6` |
| Uhlový krok | `5336` | `53E8` | `53F8` | `53F8` |
| Projektilové podkroky | `5338` | `53EA` | `53FA` | `53FA` |
| Režim plánovača | `45F8` | `46A8` | `46B8` | `46B8` |

Frame helper 1.10 `3:D74A` používa `low32(sign_extend_16(53F4) * time_ms) / 1000`. Pri zmene výsledku tiež zvýši vlastné logické počítadlo len raz. Ponechať 32-bitové orezanie je súčasť verného modelu; ide o primárne bajty `MUL`, vymazanie EDX a `DIV`, nie o neobmedzené celočíselné násobenie.

### 2.3 Streľba a oheň: oprava jednotiek

Vo všetkých štyroch EXE je DS `01F6..01F9 = 02 01 03 01`, DS `01FC..01FE = 64 0A 02`.

`AA90(1, …)` zvýši counter DS `01FA`, saturujúci na 255. Pomalá aktualizácia ho volá raz na krok. `AA90(0, edge)` prijme výstrel až po dosiahnutí prahu, vynuluje counter; weapon index 3 povoľuje držaný vstup, pri ostatných vetvách sa používa hrana. Vstup potom volá vlastnú streľbu, v ktorej ešte platia ďalšie podmienky.

| Index zbrane | Prah slow krokov | Nominálny ustálený čas prahu pri 8 Hz |
|---:|---:|---:|
| 0 | 2 | 250 ms |
| 1 | 1 | 125 ms |
| 2 | 3 | 375 ms |
| 3 | 1 | 125 ms |

Tieto časy sú **odvodené**, nie odmerané výstrely. Fáza vstupu voči ďalšiemu ticku, ammo, pool projektilov a zbraňová animačná vetva môžu výslednú kadenciu zmeniť. Nejde o dôkaz, že každá zbraň strieľa presne každých uvedených X ms.

Kontaktný oheň odoberá 100/10/2 HP za **slow update**, ak prejde jeho class/invulnerability brána. Pri dostatočne častom plánovaní v mode 0 je odvodené tempo stredného/malého ohňa 80/16 HP/s. Veľký oheň pri HP ≤ 100 zabije pri prvom prijatom škodovom update. Výraz „damage × 1000 / 53F2“ zo staršieho auditu je nesprávny pre túto vetvu.

### 2.4 Poradie frame vetvy a cache projekcie

Win16 1.10 `3:DA4B–DA80` potvrdzuje toto poradie; 1.3/1.6/1.8 majú zodpovedajúcu postupnosť:

1. `D8FC`: osobitná otáčacia/stavová vetva.
2. `D78C`: zvýšenie generácie a render/projekcia.
3. `BBCA`, `BA54`: nadväzujúce hráčske/HUD vetvy.
4. `1E00`: posun dverových záznamov.
5. `9E20`: aktualizácia projektilového poolu vrátane kolízií.
6. `3AB8`: prezentácia, preskočená pri `46B6 == 8`.
7. `9806`: spracovanie vstupu, pohybu hráča, streľby a USE.
8. Nastavenie nasledujúceho frame deadline/counteru.

**Potvrdenie:** render v tejto vetve predchádza aktualizácii projektilov i vstupu. Nie je správne automaticky rekonštruovať poradie „vstup → všetka simulácia → render“.

**Čo sa tým neuzavrelo:** `OBJECT+18` sa v `3:CC7C` zapisuje len po prechode projekčnými/viditeľnostnými podmienkami a pridelení sprite slotu. Samotné skoršie zavolanie renderu teda neobnoví cache každého objektu. Pri projektilovom zásahu mimo tejto cesty stále treba porovnať posledný zápis +18 a čas damage. Poradie je staticky uzavreté; univerzálna aktuálnosť poľa zostáva Unknown.

### 3.1 Paleta: 1.8 → 1.10

Posledný rozdiel je priamo v inštrukciách: 1.8 `3:3326 push 4D9A`; 1.10 `3:33C8 add bx,4D9A` a `3:33CD push bx`, pričom BX už obsahuje `index*4`. Cieľ importu je `WING#1006`.

Identifikácia API je podporená dokumentáciou Microsoftu; Win16 ABI argumenty boli pri vybraných callsite-och kontrolované v assembleri. [GetDeviceCaps](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-getdevicecaps).

Vizuálny dosah na konkrétny ovládač a skutočný obraz pri fade/dark evente je **Unknown** do runtime porovnania. Programátorsky treba tieto rozdiely ponechať pri emulácii konkrétneho vydania.

### 3.2 Zvuk: 1.6 → 1.8

Win16 1.8 `3:E016` a 1.10 `3:E0C4` pri inicializácii získajú pôvodné MIDI a wave hlasitosti do DS `3A5C` a `3A60`, zaznamenajú úspech do `3A64/3A65` a pri ukončení podmienene obnovia uložené hodnoty. V zodpovedajúcich init/cleanup rutinách 1.3 `3:DDA4` a 1.6 `3:E016` tieto get/restore volania nie sú.

Presné callsite-y 1.8: `E07A` MIDI get, `E091` wave get, `E18B` MIDI restore, `E1A2` wave restore. NE importy `MMSYSTEM#211/#415/#212/#416`; C export ich identifikuje ako `midiOutGetVolume`, `waveOutGetVolume`, `midiOutSetVolume`, `waveOutSetVolume`. Stav: Confirmed / High pre tieto cesty. Úspešnosť na každom historickom zariadení sa tým nedokazuje. [MIDI volume API](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-midioutgetvolume), [wave volume API](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/nf-mmeapi-waveoutgetvolume).

### 3.3 Voliteľný úvodný obrázok v 1.6

Medzi 1.3 a 1.6 pribudla v exporte cesta `1.6 4:2E68 → 3:5AF2`. Pokúša sa načítať `dstopen.img`; dekóder číta 128-bajtový header s úvodným bajtom `0A` a RLE bajty `C0..FF`, vykresľuje po 320-bajtových riadkoch do 200 riadkov. Po úspechu caller zobrazí obraz a čaká 2 000 ms. To podporuje označenie **PCX-like loader**. Presný viditeľný obrázok zostáva Unknown, pretože `dstopen.img` v rozbalených troch shareware balíkoch nie je. Prítomnosť kódu nie je dôkaz, že sa obrázok pri každom štarte zobrazí.

### 4.1 E1M5: premiestnený objekt

Header `MAP.1` je v trojici rovnaký a počet blokov je 11. Pri mapovom vzorci `514 + (map_index*8192) + ((y*64+x)*2) + layer`:

| Súborový offset | Mapa | Súradnice od nuly | Vrstva | 1.3/1.6 | 1.8 |
|---|---|---|---|---|---|

ID `D8` má v zhodnej objektovej class tabuľke triedu `27h`. Presný asset názov tu nie je odvodený zo všeobecného názvu triedy. Posun predstavuje rozdiel dát, nie automaticky zmenu kódu AI. Confirmed / High.

### 4.2 GAME.PAL máme pre tieto tri balíky

Tento `GAME.PAL` má 5 459 bajtov a je **8-bitový PCX 320×200**, nie holých 768 RGB bajtov. Na `0x1252` je marker `0C`; nasledujúcich 768 bajtov od `0x1253` tvorí 256 RGB trojíc. Nezávislé dekódovanie cez Pillow potvrdilo rozmer, režim P a zhodu palety s poslednými 768 bajtmi súboru.

## 5. Register funkcií a význam jeho čísel

`all_windows_function_blocks.csv` obsahuje každý rozpoznaný blok `FUN_*` zo štyroch exportov: zdroj, verziu, riadky, signatúru, hash tela, priame volania a indikáciu nepriamych volaní. Súčet 3 856 zahŕňa verzie tej istej rutiny opakovane, nejde o 3 856 odlišných funkcií hry.

Konzervatívne porovnanie tvaru C tela s adresovanými symbolmi premenovanými podľa poradia výskytu našlo voči 1.10 jednoznačných kandidátov 450 v 1.3, 490 v 1.6 a 514 v 1.8. **Toto nie sú percentá pochopenia ani dôkaz behaviorálnej zhody.** Normalizácia zachováva literály a opakované identity symbolov, ale nezaručuje rovnaké globálne dáta, volaných adresátov či správny dekompilát. Zvyšok zahŕňa zmeny, nejednoznačné malé funkcie a odlišné chyby exportu; nemožno ho nazvať „všetko neznáme“.

Predchádzajúci tracker 65 dokončených ručných auditov sa týmto automaticky nezvyšuje. Tento prechod dodáva samostatné overené otázky a dôkazy; export 52 vybraných C/ASM dvojíc tiež nie je dôkaz 52 dokončených 12-bodových auditov celých funkcií.

## 6. Čo ostáva neznáme naprieč Windows verziami

Register sa sústreďuje na otázky, ktorých odpoveď môže zmeniť rekonštrukciu. „Zostáva staticky“ znamená, že práca nemusí čakať na používateľov debugger. „Runtime“ znamená, že treba skutočný beh na presnom builde; video samo osebe spravidla neukáže hodnoty polí.

| Úplnosť verzií | 4 jedinečné EXE overené hashom | Ďalšie Windows/registered buildy: inventarizovať len po získaní ich EXE a dát. |

## 7. Konkrétne runtime overenia

Nasledujúce testy sú návrhy; **neboli vykonané**. Najprv spárovať dynamický selector so segmentom NE daného hashu. Uložiť EXE/asset hash, mapu, hráčsku polohu, smer, režim, čas a vstupy. Nepoužívať číslo NE segmentu priamo ako selector v debuggri.

1. **Časovanie:** v 1.10 sledovať `D70A`, `D974`, `D74A`, `D78C`, DS `0228/022C/0230/0234`, `46B8` a ms clock. Pri mode 0 a plynulom behu očakávať približne 8 slow update-ov/s; pri riadenom prerušení overiť, že nevznikne catch-up séria.
2. **Kalibrácia:** breakpoint po `D863` a po `D89B`; uložiť `53F2`, lokálne D a `53F4..53FA`. Rozlíšiť surový čas a hodnotu s minimom 40. Pre ostatné verzie použiť tabuľku vyššie.
3. **Cache damage:** `CC7C` pri zápise OBJECT+18, následne projectile collision/damage `9B64/80F8/9FA2`. Porovnať objekt viditeľný, za okrajom a po rýchlom otočení; zaznamenať poslednú generáciu zápisu.
4. **Paleta 1.8 vs 1.10:** zmena jednej nenulovej indexovej farby v rovnakom stave; pri `32B2/3360` zaznamenať index, odoslaný RGBQUAD a framebuffer spolu s paletou. Opakovať pre `RC_PALETTE` vetvy.
5. **Zvuk 1.6 vs 1.8:** pôvodná hlasitosť → zmena v hre → riadne ukončenie; log get/set návratov odlíši podporu zariadenia od kódu obnovy.
6. **E1M5 dáta:** porovnať bunky (26,34)/(26,35) od nuly v rovnakých balíkoch; cieľom je potvrdiť viditeľný objekt 0xD8 a následky presunu, nie hľadať zmenu AI v EXE.

## 8. Implementačne použiteľné výsledky

- Zaviesť build profil podľa hashu. Oddeliť EXE identitu od identických/odlišných assetov.
- Zachovať dva bucket counters a rozdiel mode 0 / nenulová vetva; nepridávať catch-up slučku do kompatibilného režimu bez označenia zmeneného správania.
- Uchovávať surový priemer render merania oddelene od lokálnej efektívnej hodnoty a odvodených krokov.
- Neodvodzovať GUARD, fire hazard a counter 01FA z aktuálneho FPS.
- Zachovať poradie projekcia/render → pohyb dverí/projektilov → prezentácia → vstup, ak sa rekonštruuje táto pôvodná frame vetva.
- Pre 1.10 rozlíšiť paletové vetvy a správny `RGBQUAD[index]` pointer. Staršie správanie neopravovať potichu pri tvrdení presnej emulácie staršej verzie.
- Pri 1.8/1.10 obnovovať úspešne načítané pôvodné hlasitosti pri príslušnom cleanup.
- Pri dátovej kompatibilite nepovažovať rovnakú veľkosť MAP za zhodný obsah. Zachovať verziu presunu D8.
- Paletu z dodaného GAME.PAL načítať ako PCX paletu; interpretácia súboru ako prvých 768 RGB bajtov je nesprávna.
- Neznáme CLASS overlays, všetky animation alternates a cache freshness ostávajú `TBD`.

## 9. Overenie, súbory a istota

Vykonané: hashovanie EXE/exportov/assetov; NE segmenty a relokácie; úplný parse 3 856 `FUN_*` tiel; vybrané C/ASM kontroly; byte anchors pre 8 Hz, kalibráciu a tabuľky v každom EXE; presný MAP diff; nezávislé PCX dekódovanie. Aritmetické príklady v `verification.json` sú modely získané z inštrukcií, nie záznamy behu Nitemare3D.

Dôkazový ZIP obsahuje registre CSV, `ne_metadata.json`, presné výrezy pre každý build, extrahovanú paletu, validačný výstup a reprodukčné skripty. Plné pôvodné hry sa do výsledku znovu nepribaľujú. Pri reprodukcii použiť pôvodné vstupy uvedené v inventári; podrobný postup je v README.

Celková istota: **High pre uvedené priame bajtové/dátové zistenia; Medium pre interpretáciu viditeľných dôsledkov bez behu; Unknown pre otvorené oblasti.** Celkové percento dokončenia sa týmto auditom nevypočítava. Predchádzajúca zhoda funkcií, automatické pokrytie a runtime potvrdenie sú tri odlišné metriky.
